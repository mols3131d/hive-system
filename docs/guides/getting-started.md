# Get started with Hive

Choose the Hive data workspace and its reviewed policy revision independently of the project you are editing. Confirm the user's selected collaboration backend before accessing records. Use Dolt v2 for the adopted MVP developer workflow and follow the pinned v1 procedure below for existing Markdown/Git workspaces. Keep the CLI, data and optional agent assets in explicitly authorized local destinations outside external projects.

## Install the v2 CLI

Use a reviewed Hive system revision and its locked Rust dependencies. For the owned v2 runtime and guarded writes, use Linux on a supported local filesystem with procfs and verified Dolt 2.7.6. Check the [runtime requirements and workspace layout](../architecture/dolt-workspace-contract.md) before using a workspace. From the reviewed checkout, select an explicit, user-owned installation root outside the system and external project trees:

```sh
cargo install --locked --path . --root /absolute/path/to/hive-install
/absolute/path/to/hive-install/bin/hive --version
/absolute/path/to/hive-install/bin/hive --contract 2 workspace doctor --help
```

Record the reviewed source revision with the binary version. Use the installed executable by absolute path or through a user-selected `PATH`. Installation and workspace initialization, registration and runtime start are separate actions. Use the [bootstrap procedure](../development/README.md#dolt-workspace-initialization) only for an explicitly authorized new workspace. The [v2 Skill](../../agents-configs/README.md#install-the-v2-skill) is optional and uses the same CLI.

## Inspect or resume v2 work

Begin in read-only mode. For an existing workspace, pass the explicit root to `hive --contract 2 --json workspace doctor --workspace PATH` and `hive --contract 2 --json workspace status --workspace PATH`. An offline status is an observation of local state. Add `--workspace-id UUID --database NAME --port PORT` with the authenticated reader environment for committed identity verification. Use the checked workspace and explicit endpoint on subsequent reads. Review the exit status and JSON envelope before using its data. [Workspace status contract](../architecture/dolt-workspace-contract.md#workspace-status)

Use `hive --contract 2 --json context resolve` for scoped resumption, `issue show` for a selected Issue or `issue ready` and `issue blocked` with an explicit Area or Project. Resolve against the pinned policy checkout and clean asset revision with the selected actor and role or registered Queen. Use only the bounded result and authorized exact references. Keep management files and private conversation bodies out of runtime context. If a required handoff or directive cannot be resolved, report the gap and pause the affected action. [Context inputs](../development/README.md#v2-current-context) · [Context contract](../architecture/dolt-mvp-contract.md#context-resolution)

Manual operation follows the same guards as the Skill. An inspection or context resumption request leaves the runtime and Claims alone. For authorized work, verify a current execution-scoped Claim and current request-bound evidence before acting. Preserve concise Issue notes and a handoff for the next session. Confirm the exact execution stopped before release, recovery or submission. Use independent review for acceptance. If a commit is ambiguous, inspect the original request and reconcile it before further writes. Only a human-authorized Queen may publish externally under applicable Directives. Workers use authorized external reads and prepare drafts in Hive. If a required contract, tool or authority is unavailable, report it and use only authorized manual inspection within the verified scope. [Workflow and decision contracts](../architecture/dolt-mvp-contract.md#shared-skill-procedure)

Explicitly import only user-selected Markdown for an active Queen. Historical conversation reads and local export are separate from work resumption. Local backups omit conversations by default. To carry conversation history in a backup, explicitly include it at backup time and select it again when restoring to a separate inactive target. [Conversation operations](../development/README.md#import-a-queen-conversation) · [Backup and restore](../development/README.md#create-a-local-workspace-backup)

## Operate a pinned v1 work bundle

Use these manual, document-first procedures in the explicitly selected v1 data workspace. The public system repository contains the shared contracts and optional [templates](../../assets/templates/README.md). Use authorized Git and file tools in the data workspace. Choose that workspace independently of the project you are editing. Keep Hive state and optional harness assets out of external projects unless a project-owned integration is separately authorized. An explicitly opted-in ignored `.local/hive/config.yml` may supply a local connection binding. See [configuration and identity](../architecture/system-design.md#configuration-and-identity).

1. Confirm the target project or non-project scope, source ref where applicable, intended outcome and authorized account. Apply the [collaboration backend selection](../policies/workspace/organization.md#collaboration-backend): use Hive unless the user explicitly designated Notion; in that case do not follow the remaining Hive-specific steps. Resolve the [project or reserved scope ID](../policies/workspace/organization.md#project-identity), then locate or create a work bundle in its appropriate [task management area](../policies/workspace/tasks.md). Write its `README.md` with the goal, applicable acceptance criteria and relevant references; set progress metadata for active work.
2. Before consequential work, check [decision and action authority](../policies/workspace/organization.md#decision-and-action-authority), [project specification policy](../policies/workspace/organization.md#project-owned-specifications) and [external repository boundaries](../policies/workspace/organization.md#external-development-repositories) where applicable. Work within the authorized scope. If the workspace has adopted the [Git-backed task coordination contract](../policies/workspace/tasks.md#git-backed-issuance-and-claims), confirm issuance, selection and the responsible claim at its authority before executing. Direct tools may do so only if they can meet its revision guards; otherwise stop affected operations. Save a research, plan, review, report or other artifact only when it has a future reader or delivery purpose. Put it in the work bundle's `artifacts/` directory; use root `artifacts/` for independent deliverables. Do not create a work item just to store a standalone artifact.
3. For long-running work, retain useful continuation context in the task or a concise [handoff](../policies/workspace/communication.md): material decisions, relevant source revisions, confirmed progress, blockers and next action. Save reports, briefings and material discussion outcomes when they help the developer review or decide. One artifact can suffice. Re-resolve the bundle and source revision when resuming; a commit does not deliver a message or activate another session.
4. Review actual acceptance and verification. Under the adopted coordination contract, reconcile or release the current claim before closing and confirm the lifecycle change at the authority. Update active progress metadata without moving the bundle. Move it only at selection, closure or authorized reopening; check affected references and retain the closed outcome and date. Put human-facing reports with their owning work or in standalone artifacts if independent. Retain temporary specifications only as conditional work artifacts; do not promote them automatically to project records.

Follow [Git publishing](../policies/workspace/git-writes.md) and [retention](../policies/workspace/lifecycle.md). Never persist raw conversations or routine session context.
