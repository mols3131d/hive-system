# Dolt v2 MVP Contract

This contract defines the Dolt v2 MVP development baseline adopted in [#22](https://github.com/mols3131d/hive-system/issues/22#issuecomment-7198810176) and reconciled with the product identity, role, authority, and continuity decisions in [#34](https://github.com/mols3131d/hive-system/issues/34), including the proposed minimal Queen conversation import/read boundary and proposed MVP deferral of Bot curated Memory operations. Read it with the [architecture overview](dolt-redesign.md) and [relational schema](dolt-schema.md). The command syntax, limits and DDL guide implementation and require verification through the [acceptance matrix](#acceptance-matrix-and-evidence), preserving the pinned initial migration, stable IDs, and domain guards. Existing workspaces follow their reviewed v1 policy pins. Live migration and an authority switch require separate explicit operator approval.

## Domain and identity

One authoritative local database per workspace. Area is an untyped recursive scope with a stable UUIDv7 (application-generated, CHAR(36), normalized lowercase). Sub-area is an Area with a parent. Require one owning Area per Issue; an explicitly selected general Area is allowed, never an implicit fallback. Enforce sibling slug uniqueness including roots and prohibit cycles. Moving an Area preserves all IDs. Archive an Area only with no active claims in its subtree; archived ancestry excludes execution and new work until explicitly restored. No automatic archival of children or related Projects.

Project is an independent purpose-based collection of Issues. Membership is optional and many-to-many across Areas. Removing a membership or completing a Project never closes an Issue. Explicitly completing a Project is a planning decision, not acceptance of all members. MVP has no custom project fields, milestones, iterations or project-specific execution status.

Use UUIDv7 primary keys and an immutable workspace-wide issue number for human references (#42). Allocate under the authoritative write lock using a counter row in the same transaction; no MAX+1, reuse or offline allocation on replicas. Import preserves a qualified legacy ID mapping, not necessarily legacy numbers. On restore prohibit concurrent old authority before writes. Area slugs and Bot slugs are locators, not identity. Priority 0–3 (0 highest), NULL unspecified, ordering by priority then creation then ID/number; no priority grants authority. Labels are workspace-wide and unique under the schema's `name` unique key and installation collation (`VARCHAR(100)`). Future create-time canonicalization trims only leading and trailing Unicode whitespace from the input, requires a nonempty stored name of at most 100 characters with no control characters, and preserves spelling, accents, and interior spaces without case-folding, Unicode rewriting, or duplicate detection beyond SQL. Epic is a grouping Issue, not an executable claim target. Feature, Task and Bug may execute. Parent hierarchy and prerequisite DAG are independent; cross-Area references are allowed with explicit authority. Related/discovered-from links may be deferred; do not misrepresent either as a dependency.

## Work lifecycle and accountability

| Command / transition | Invariant |
| --- | --- |
| create -> backlog | Capture goal; no Claim |
| select backlog -> todo | Verified scope, actionable acceptance criteria, authority; epic may be selected for planning |
| claim todo -> in-progress | Non-epic, ready, fresh expected revision, no active claim; allocate unique claim and holder |
| release/recover in-progress -> todo | Exact claim and verified execution stop; recovery requires authorization |
| submit in-progress -> review | Accepted prerequisites and verified execution stop. Record evidence and result, then remove the claim atomically |
| request-changes review -> todo | Record reviewer feedback; new claim required |
| accept review -> done | Authorized acceptance, recorded outcome, accepted prerequisites, resolved required children and absent claim |
| submit-epic todo -> review | Explicit proposal with accepted prerequisites and resolved required children. Epics have no execution claim |
| cancel nonterminal -> cancelled | Explicit authority and outcome; in-progress must first be explicitly released/recovered with matching stop evidence |
| reopen done/cancelled -> todo | Explicit reason/authority; reset closure fields; reconcile downstream and parent outcomes |

Only in-progress may have an active execution Claim; it must have exactly one. Holder is an opaque authorized execution reference, not necessarily a persistent Bot. Planned assignment and reviewer assignment are not exclusive claims; defer a separate assignee field. Claim is not runtime control, credential, or execution permission. No lease, heartbeat, automatic expiry or reassignment in MVP. Stop uncertainty blocks release/recovery/acceptance rather than granting ownership. Epic acceptance requires all children terminal; cancelled children require explicit documented acceptance of the changed scope. The same child-resolution check applies to any parent with children; parentage does not itself create prerequisite edges. Validate a combined completion-obligation graph (Issue -> prerequisites and parent -> children), rejecting cycles even when the individual graphs are acyclic. This check prevents completion deadlocks and does not make parentage a prerequisite or alter ready filtering. Only accepted done satisfies dependencies. Check prerequisites again on submission and acceptance, including for epics that never execute a claim. Reopen, dependency/parent edits and other changes that invalidate accepted work, current review submissions or running work require explicit reconciliation; reject otherwise. A new unmet prerequisite or changed acceptance criteria cannot silently invalidate a running or review Issue. An accepted parent cannot acquire an unresolved child or retain an invalidated child outcome without explicit reconciliation. Reopen/reconcile affected accepted parents and dependents in reverse completion order using existing guarded transitions before changing the prerequisite or child; do not require an unspecified bulk reconciliation command. Running dependents must first be safely released; review dependents must first receive request-changes. Reject changes if the affected state still violates invariants. No implicit cascade or reopening. Keep progress, evidence, handoff and review notes as intentional typed Issue updates, not logs. Every successful lifecycle transition also appends a system-generated typed transition update in the same transaction, including exact Claim ID/holder and stop/result/review evidence refs where applicable. Stop evidence must bind the exact Issue, Claim ID and holder, explicitly attest execution stopped, and identify source/observation time; reject evidence for an older claim or a session event alone. A submission is resolved by its typed transition and current state/revision chain, never by timestamp alone; nonsemantic note edits need not invalidate it, but review always binds the current Issue revision. Acceptance/request-changes must bind the current submission transition and expected Issue revision, and compare the reviewer reference against the submitter and recorded execution holder even after the Claim row is removed. These checks concern workflow references, not authenticated human identity. Generic issue note cannot create or alter transition records.

Ready = todo + executable type + no hold + no current Claim + accepted prerequisites + no archived Area ancestry. Blocked = executable todo not ready, with reason codes; epics are planning-only. Do not store ready/blocked status. Readiness does not grant permission. Claim re-evaluates the predicate in the write transaction.

## Canonical ownership and files

| Data | Canonical owner |
| --- | --- |
| Structured collaboration records, Issue body and updates | Dolt |
| Directive and textual Artifact Markdown body | Dolt |
| Registered Queen (`bots`) registry and Area/resource relations | Dolt |
| Queen Soul (`SOUL.md`) | Native Git tracked Markdown file |
| Preserved Queen conversations (human recall) | User-owned UTF-8 Markdown in a private local data root outside Git worktrees, Git Soul assets, and Dolt; explicit user-selected import/read path, excluded from context and ordinary backups by default, with optional explicit export or backup inclusion |
| Bot curated memory (`bot_memories`) | Preserved in pinned `0001_initial.sql` for SQL/migration compatibility; Bot-specific curated Memory operations (`memories/LATEST.md`, `memories/core/`, `memories/references/`) are proposed deferred for MVP dogfooding |
| Large/binary external assets and team collaboration records | Existing authorized canonical owners; Resource or Issue reference without lifecycle mirroring, mandatory sync, or unrestricted copying |
| Machine config, resource path bindings, local credentials | XDG local environment; never shared |

MVP does not require a managed binary blob store. Reference externally owned files without copying; optional immutable managed blob storage and its recovery protocol are later features. For text artifacts, store Markdown once in Dolt, export on request as a noncanonical copy. Artifact has optional explicit Area, Project, Issue and Resource joins, can be standalone, and does not inherit issue status. Context lookup never treats a matching join as permission to disclose a multi-scope body: default summaries use only directly selected scope/Issue links and explicit workflow scope, without expanding unrelated links. A full body requires explicit selection and coverage of its linked scopes, or an explicit exact-record workflow disclosure declaration; standalone artifacts require explicit selection. Apply this gate to all body-returning reads (including artifact show, exports and explicit handoff/evidence bodies), not just Context Resolver. Metadata is title/kind/ID/revision from fields already in the record, never an inferred body summary; suppress titles/links when their scope is not selected. Unselected or out-of-scope relation details are not returned. Apply the same rule to cross-Area prerequisite, parent and Resource references; return only permitted metadata or an opaque blocker, not unrelated body text. Preserve existing artifact retention default (three months from applicable substantive event) and work record minimum retention (seven days after relevant event), with retention exceptions, open references and claims protected. No automated deletion or history erasure. Explicit durable archive or verified transfer to canonical owner is a separate decision.

Directive has exactly one scope: workspace, Area or Project. Area descendant applicability is an explicit flag, default false. A project directive applies only when that project is explicitly selected and, if an Issue is selected, the Issue is its member; membership alone is not applicability. An explicitly selected Project-only context may include its directives without sweeping member Issues or their Areas. Workspace/Area ancestry, selected Project, and current Issue are query dimensions, not trust or authority grants. Check source, issuer, validity interval and approval provenance. Conflicting applicable directions stop the affected action for resolution; specificity is not an automatic permission override.

Bot is a registered persistent **Queen** identity by definition. Multiple registered Queens are permitted in one workspace with no one-to-one Queen–Project mapping, and one Queen may have multiple concurrent independent sessions. Registration stores DB metadata without a role column or selector; the sole required Bot content asset is `assets/bots/<slug>/SOUL.md`. **Overlord** and **Drone** are logical coordination and execution responsibilities, not independently registered Bots, and need no independent `SOUL.md`, durable session archival, or Bot Memory. A Queen may coordinate or execute work directly without changing Queen identity. Role policy remains system-owned. SOUL body contains only identity/purpose/persona for injection; strip management frontmatter from runtime payload. Queen identity is distinct from session identity: track execution responsibility and Claims at execution/work scope rather than treating all sessions of one Queen as one holder. Bot-specific curated Memory operations (`bot_memories` mutations and `memories/` views) are proposed deferred beyond MVP dogfooding while preserving the pinned `bot_memories` table and v1 compatibility; where curated memory is later enabled, latest and durable (core/reference) memory use explicit Bot and exact Area scope with no automatic parent/descendant sweep and no required files in the asset tree. Do not load README/AGENTS as Bot runtime context; verify host auto-discovery behavior or refuse that activation path. Registry validation checks safe relative paths, expected files and no symlink escape. Registration: prepare and validate asset files and Git commit first, then record registry; failure leaves unregistered files not loadable as a Bot. File edits remain reviewable and independent; capture exact file revision for context. A registered Bot's Soul must be present and valid in the selected committed asset tree; a dirty/unregistered file is never an activation input. Keep registration's exact reviewed asset commit in mutation provenance and validate the selected Soul blob independently on each later activation. No mandatory DB write just to change the independently owned Soul. No atomic SQL+Git claim. Preserve user-owned readable Queen conversations for human recall through an explicit user-selected UTF-8 Markdown import and read path stored in a private local data root outside Git worktrees and the Git-tracked Soul asset tree; validate workspace and Queen identity before importing, keep sessions separate, exclude conversation bodies from `context resolve` and ordinary Dolt/Soul backups by default (requiring deliberate export or explicit backup inclusion for portability), and never use implicit host capture, raw host session reads, secrets, personal data, or generalized Overlord/Drone execution logs.

## Local runtime and authority

Use the Rust CLI and local Dolt SQL Server (MySQL protocol). Preserve reusable CLI/config/JSON code. Go embedded is a fallback only if measured setup, latency or reliability warrants a rewrite; CLI subprocess access is a bootstrap/diagnostic candidate, not the normal per-query data path. Pin Dolt and Rust dependency versions and verify supported versions at doctor/start. One local server per authorized workspace, explicit start/stop; no auto-install, background scheduler, service registration, external bind or remote exposure. Prefer a private Unix socket and restrictive permissions where supported; otherwise authenticated loopback with unique endpoint. Disable or secure default root access, use limited writer/read-only credentials, redact diagnostics. No credential in Git, DB records, command argv or logs. No Hive HTTP daemon required.

Use an OS-held exclusive advisory lock per canonical workspace for all Hive mutations, maintenance, backup/restore and sync; process death releases it. Local filesystem only, no independent clone or multi-host writers. Use a stable workspace-ID-keyed lock and active-root registration in the single configured local Hive state directory; verify canonical root and DB identity against that registration. A restored copy at another root stays inactive; never create a second active lock just by changing its path. Different state-directory configurations or machines cannot guarantee mutual exclusion; independent writable copies are unsupported. No deleting lock files or stealing based on age. All participating writers must use the lock; direct Dolt administrative writes are explicit offline maintenance with full validation, not normal operation. Raw DB access is not a security boundary against the same OS user. Use read-only access for UI and analysis; do not expose arbitrary mutation SQL. If lock tests or process ownership fail, refuse writes; prefer a verified single writer rather than assuming Dolt merge semantics provide serializable graph invariants. The previous mutation_guard token remains an alternative experimental conflict check, not an MVP dependency.

With lock held, verify storage authority and request identity, resolve existing receipts before checking expected revisions for new mutations, and require a clean/compatible branch main. For a new request, persist a bounded local pending-request marker before attempting commit; begin one SQL transaction, revalidate affected state, apply all changes, store an operation receipt, commit, verify the committed result, then clear the marker before success. Prototype session dolt_transaction_commit=1 with explicit transactions, force-commit disabled; test actual durability/rollback and version commit behavior. Record request ID, operation kind, request fingerprint (no raw confidential payload), result IDs and new revision in the same transaction. On ambiguous result, reconcile by request ID at the authoritative version. A matching fingerprint returns the prior result and a changed fingerprint conflicts. A missing receipt is inconclusive while the earlier server transaction may still publish. Do not blindly retry or assign execution until verified. Version commit hash is discovered after commit, not written into that same commit. Hold lock through confirmation. If SQL and version commits separate in the tested release, define recoverable pending-publication state before adopting; block subsequent mutations until reconciled. No global ownership from independent replicas.

## XDG and configuration

Select the CLI contract before reading config or resolving a workspace. V1 keeps its current XDG config and bindings. V2 reads XDG_CONFIG_HOME/hive/v2/config.yml (default ~/.config/hive/v2/config.yml) and v2 Area/resource bindings. Its default data candidate is XDG_DATA_HOME/hive/v2/userdata/ (default ~/.local/share/hive/v2/userdata/), containing db/ (Dolt), assets/ (Git Bot files), conversations/ (private local Queen conversation UTF-8 Markdown files outside Git worktrees and `assets/`, with restrictive `0700`/`0600` permissions where supported), and a nonsecret workspace descriptor. Require the selected contract's workspace marker and compatibility before using the target. V2 uses XDG_STATE_HOME/hive/v2/ (default ~/.local/state/hive/v2/) for locks, recovery state and redacted diagnostics. Use a private XDG_RUNTIME_DIR/hive/v2 socket when available. Never track Dolt internal files or private Queen conversation files in ordinary Git. No secret or host-specific mapping in shared files. Absolute XDG paths only; fallback per specification; explicit invalid selection is an error. Resolve explicit CLI workspace/Area/Project > explicitly configured applicable local binding > user default > validated XDG candidate. A Resource may map to several Areas; return candidates, never silently choose. Project bindings become Area/resource bindings with optional explicit Project; non-Git resources work without Git root. No automatic writes to external projects.

## Backup, sync and migration

Local-first; no remote required or per-change push. MVP consistent backup: quiesce writers and asset edits, verify clean committed DB and asset Git revisions, export to isolated destination with a manifest containing workspace ID, schema version, Dolt commit, asset Git commit and digest of snapshot files; omit credentials and host paths. Preserve this paired Dolt and Soul Git backup contract intact: ordinary backups exclude private Queen conversation files by default, and deliberate conversation export or explicit opt-in backup inclusion is required for portability (verified with synthetic files before accepting D05). Validate restore on a fresh target before promoting, verify graph/claims and Soul files (and explicitly included conversation files if opted in) and prohibit overlapping execution authority. Ordinary Git remote is a candidate for Dolt remote; do not conflate Git refs with database refs. Optional remote backup only after synthetic restore and privacy checks. Paired DB/file remote publishing is not atomic; combined remote sync/pull/merge deferred until manifest publication and partial failure recovery are proven. No automatic conflict merge, force push, or independent offline claim coordination.

Migration: inventory legacy files read-only, stop/handoff affected agents, preserve exact old Git ref and policy pin. Produce explicit mapping old scopes -> Areas, Project collections and Issues; preserve references and historical revision evidence. Choose the mapping using the pinned v1 policy, lifecycle directory, status, claim and retained evidence. Backlog and unclaimed todo can map when their required provenance is available. A claimed todo or review, any running or uncertain claim, and review without typed submission provenance require reconciliation first. Active done awaiting closure and archived terminal records require evidence for the selected v2 terminal state, including closure time, actor and outcome. Preserve the exact source Git reference and the reason for excluding unresolved records from the operational import, including valid v1 records with missing provenance. Retain unknown dates without manufacturing a value, acceptance or claim transfer. Map reserved general/userdata scopes explicitly, never infer from repository name. Import directives, text artifacts and bot metadata into Dolt; preserve legacy v1 file-memory inventory and mapping prerequisites read-only for compatibility (and only import into `bot_memories` if curated memory is enabled in a reviewed adoption), keep Soul in the asset tree, and never treat navigation-only files as facts. Preserve uncertain observation dates as unknown. Old memory files remain legacy sources until cutover; no dual canonical originals. Use a new DB/asset tree, dry run on a copy, compare counts, hashes, semantic relationships, missing references, retention and context boundaries; produce import report and legacy ID map. Stop old authority before cutover, obtain approval, update policy and config atomically at the authority-selection boundary. Keep source snapshot read-only for rollback; once new writes occur, rollback requires reconciliation, not silent switch. See the [v1-to-v2 migration mapping design](dolt-migration.md) for surface mappings, evidence and rollback verification.

Test DDL, unique IDs/numbers/root slugs, FK and graph constraints, all lifecycle transitions, claim races, lock crash/recovery, commit ambiguity/retry, forbidden mutations, backup/restore, safe paths and host context exclusion on synthetic fixtures. ## Detailed MVP review contracts

The detailed contracts apply the selected Soul and Memory storage boundary to Bot context, CLI, runtime and recovery. Verify the initial numeric limits, command syntax and candidate schema during implementation.

### Bot and curated memory

Keep system-owned Role policy, user-owned Soul, preserved Queen conversations, curated context/memory, work records, and harness-owned sessions distinct. Target v2 uses **Queen**, **Overlord**, and **Drone** as logical responsibilities and policy categories distinguishing three policies—internal Hive work authority, external representation, and durable session retention—rather than fixed process types, model configurations, or a mandatory runtime hierarchy:

| Role | Responsibility | Hive authority | External services | Durable session retention |
| --- | --- | --- | --- | --- |
| Queen | Human-facing work management, discussion, delegation, review, and limited representation | Within the human's delegated scope | Authorized reads and limited writes | Yes (user-owned readable history) |
| Overlord | Coordinate a delegated objective, decompose work, manage dependencies and workers, integrate and report results | Within delegated work and subordinate work | Authorized reads only | No |
| Drone | Execute assigned work, verify results, and produce evidence and artifacts | Within assigned work | Authorized reads only | No |

A registered Bot in v2 is a persistent **Queen** identity by definition, with no configurable identity role. Multiple registered Queens are permitted in one workspace with no one-to-one Queen–Project mapping, and one Queen may run multiple concurrent independent sessions for different topics or work. Overlord and Drone are task-scoped responsibilities, not registered identities, and need not be persistent Bots. A Queen may coordinate or execute directly; no request must traverse every role. Execution responsibility neither changes Queen identity nor grants permission. Queen identity is not a session identity: track execution responsibility and Claims at execution/work scope rather than conflating all sessions of one Queen as one holder. A runtime session reference is optional, opaque, and descriptive; it is neither an authenticated actor nor a Claim.

#### Continuity boundaries and proposed MVP scope

Distinguish three continuity mechanisms explicitly:

1. **Preserved Queen conversations (human recall):** A Queen conversation is shared human-agent collaboration history preserved in a user-controlled, readable form so the human can recall past discussions, alternatives, reasoning, decisions, and context across projects and hosts. A host session ID alone is insufficient if changing hosts loses access. The proposed minimal MVP candidate is an **explicit import and read path for user-selected UTF-8 Markdown** (a user-prepared file or a supported host export). Official documentation for [Gemini CLI](https://geminicli.com/docs/reference/commands/) documents a direct Markdown export, while [OpenCode session actions](https://opencode.ai/docs/cli/keybinds/) document exporting to an editor and a separate CLI JSON export; these references show possible user-supplied inputs, not verification of installed host behavior (native host verification remains in `#14`/`#20`). Keep imported conversation files in a private local data root (`conversations/` under `XDG_DATA_HOME/hive/v2/userdata/` or the selected workspace's private local data root) outside Git worktrees, outside the Git-tracked `assets/bots/<slug>/SOUL.md` tree, and outside Dolt (`0001_initial.sql` adds no session table). Key metadata by portable `workspace_id` and Queen identity (`bot_id` / `slug`), keep sessions separate, and run the existing workspace and Queen identity checks plus user-safe import path validation (valid UTF-8, bounded size, no traversal or symlink escape) before importing. The user selects and may redact the Markdown before import. Hive excludes worker execution logs and accesses only the explicitly supplied input. Use synthetic conversation content in development fixtures and public examples. Exclude conversation bodies from `context resolve` and ordinary paired Dolt/Soul backups by default. Use deliberate export or explicit backup inclusion for portability.
2. **Native session resume:** Reuse host-provided session continuation where available. Hive does not require exact cross-provider restoration of internal model state.
3. **Worker continuity (work continuity):** Do not require durable archival of Overlord or Drone sessions. Preserve the work of all roles through Issues, claims, progress/history, artifacts, reports, decisions, verification evidence, and handoffs so an authorized replacement worker can resume without its previous session, subject to existing ownership and stop/recovery rules.

Native host context-exclusion and committed Soul verification remain owned by `#14`/`#20`.

The selected layout is `assets/bots/<slug>/SOUL.md`, relative to the workspace root (inside the native Git asset tree), with no role directory. Use a workspace-wide unique immutable lowercase kebab-case slug as the human locator and UUID as the relational identity. Never reuse a retired Bot's slug; display name changes do not move the file. Existing paths remain unchanged until explicit migration. System Role policy is versioned with the installed system; Soul contains identity and purpose, not a competing Role policy or authority grant. Any registry identity fields explicitly present in Soul must match; do not require a duplicated role field. Optional README/AGENTS remain management-only. Reject traversal, symlinks/reparse points escaping the asset root, and invalid UTF-8. Never use a Bot asset directory as a host working directory for activation.

Use distributable Rulesync source, not generated vendor assets. Skill is instructions for the host, not an executor or approval service. ### Optional lifecycle hook boundary

Prefer mechanical and hook-callable operations. Hooks are optional thin invocation paths over the same versioned CLI/domain contract used by Skill and manual clients. Do not require a specific host, add a separate runtime or event store, or install/modify host settings automatically. Vendor event mappings and delivery/injection support must be verified per host; unsupported or absent hooks use the identical manual/Skill path. Read-only hooks are safe to repeat and have no DB side effects; no new hook event table, persistent event log or retry queue.

For advisory inspection, report failure without changing state or blocking unrelated host activity. Respect host timeout and failure semantics; if the host cannot enforce required preconditions, use explicit Skill/CLI checks or do not support that activation path. ### Installation, lifecycle and recovery

Recommended first target: Linux on a local filesystem with verified process-held locks; other Unix platforms including macOS are not claimed supported until equivalent tests pass. Installation copies verified binary and distributable Skill to explicit user destinations; no auto-start/service/host integration. Use a private runtime socket if supported by pinned Dolt; else authenticated loopback, no external listener. No ambient root/no-password access; separate constrained reader/writer identities, tested procedure privileges. Different state namespaces are not an isolation guarantee. Keep lock file inode stable; never unlink to steal.

PID reuse, stale marker and unexpected external server require inspection and safe refusal. Status distinguishes uninitialized, stopped, running, incompatible, recovery-required, unknown. No automatic repair or restart. Crash releases OS lock; next writer checks the durable pending-request marker, dirty DB working set, unresolved receipts and storage authority before any mutation. A pending marker must be reconciled even when the DB working set is clean. If SQL commit/version commit split, require explicit recovery protocol and block new writes until identified commit or rollback proven; never delete state to resolve ambiguity. Execution may continue outside Hive after DB stop; never infer worker stop from server shutdown.

Backup: take exclusive workspace lock and require quiesced asset editors; require committed DB and clean asset Git tree; refuse pending writes or unknown claims/execution state for promotable backup. Export Dolt-native recoverable snapshot with history and Git asset snapshot with history into new staging destination, not a copy of live database files. Manifest includes format version, workspace ID, schema, Dolt version/commit, asset Git commit, policy revision, relative file paths, SHA-256 digests, creation time, and consistency state; no credentials, local bindings, host paths or logs. The backup manifest records whether conversations were included. `backup create --include-conversations` writes a conversation section even when its file list is empty. It binds each selected file to the portable `workspace_id`, registered Queen and conversation ID and records safe relative paths and digests. A standalone `conversation export` produces a Markdown copy at the explicit destination. Verify actual revisions and digests before final atomic publication within same filesystem; incomplete snapshot never usable as completed backup. Explicit destination only, no network or remote push. A known active claim may be preserved in an inactive forensic snapshot only if explicitly classified non-promotable; never clear it during export.

Restore checks the manifest and format version, validates the paths and digests of selected files, and verifies exact revisions before importing into a separate empty target. Use isolated restore staging, validate schema, graph, IDs, receipt history, assets and claims; compare logical row counts and content hashes. With `--include-conversations`, require the manifest's conversation section before writing the target. Return a typed error if the section is absent. Validate its digests, paths, portable workspace ID, registered Queen (active or retired), conversation IDs and UTF-8 bodies. Restore those files into the inactive target's private root outside Git worktrees. Without the flag, verify the manifest and paired Dolt/Soul snapshot and omit any bundled conversation files. A standalone Markdown export can be supplied to `conversation import` for an active Queen. Keep workspace identity, regenerate only machine-local bindings/credentials after verification. Restore returns an inactive copy without active workflow delegations, host authorization or credentials; an operator or host must supply current applicable workflow evidence before writes. Promotion under the same workspace identity requires the old writers and external executions to be stopped and the old authority's final confirmed Dolt and asset Git revisions to be verified. Verify the target preserves those revisions, issued number history, the allocation counter, and every confirmed receipt. Review claims and pending requests under separate explicit authorization. If the final history is unavailable or the target is stale, keep the restore inactive for review. An adjusted counter alone cannot recover the missing history. Two writable copies with the same identity are unsupported. No automatic authority switch, overwrite, merge, rollback of live state or deletion of original. Malformed/incomplete snapshot remains isolated, no writes to original. Remote backup/merge remains a synthetic spike and future review item.

### Execution defaults and decision gates

Apply these v2 implementation defaults alongside pinned v1 compatibility. No new service, agent runtime, event bus, RBAC subsystem or external project modifications.

#### 1. Context and authorization

Security ownership is outside Hive. The human operator, agent provider, host harness and OS own authentication, permission prompts and enforcement, sandboxing, process isolation and execution controls. Hive is a collaboration and context system, not an IAM system, credential broker, approval UI or security enforcement layer for arbitrary agent actions. It must not install or override host security settings, require a particular provider, or promise that actor references identify an authenticated person. No independent security trust model, actor authentication, mandatory local authority manifest or separate grant registry is required.

Hive retains domain workflow guards: explicit participant references, work ownership, Claim, applicable directives, delegation and review evidence, allowed workflow operations, expected revisions and state transitions (with scoped Bot memory guards retained for post-MVP use if enabled). Keep these independent of external security permissions. A host-approved tool call alone does not establish an Issue acceptance, execution stop or scope expansion; a Hive Claim or workflow delegation alone does not authorize external tool actions. Hive validates structural evidence, referential consistency and applicable scope, not the authenticity of the host or user.

For delegated or reviewed operations, accept a versioned, nonsecret workflow evidence object or an explicit reference to such a record supplied by the operator/host. The minimal evidence binds workspace, actor reference, optional Bot, exact Area/Issue scope, operation allowlist, evidence ID/revision, source/issuer reference and applicable validity interval/withdrawal status. Reviewed decisions additionally bind the request ID, canonical payload fingerprint, affected expected revisions, outcome and reviewer reference distinct from the submitting executor where required. Reject missing, malformed, expired, withdrawn, mismatched or unresolved evidence; revalidate supplied/resolved current evidence and expected revisions at the mutation boundary. Do not infer grant scope from Project membership, parent Area, Bot identity or event name. Do not fabricate approval or assert that a matching reference proves authenticated identity. Explicit user/host workflow declarations are inputs, not security credentials. Keep only nonsecret workflow provenance in Hive records/receipts; persist the minimal validated canonical workflow evidence snapshot in the receipt at mutation time, not the raw input. It records what was declared at the time, not a live grant; no tokens, provider credentials or raw approval transcripts. An evidence file or request object can carry a bounded decision or a reference to an explicitly selected local collaboration record or operator/host source. For a new operation relying on a revocable delegation, resolve its current revision and withdrawal state through that source at the write boundary. A saved declaration alone cannot establish current delegation. An operator may supply a fresh reviewed decision bound to one exact request under the reviewed path. This requires no new registry, service or external fetch. A bare ref or previously saved receipt is insufficient for a new delegated write. For CLI and hook requests use explicit --evidence-file or an allowlisted typed evidence object in the request, mutually exclusive with a resolvable evidence ref. Use --authorization/--approval only for workflow declarations; --stop-evidence and result evidence refer to distinct work records. A hook event alone supplies neither stop nor review evidence. If the source cannot establish the current state of a revocable delegation, fail the delegated write with a typed workflow error. Host authentication and permission revocation remain outside Hive. If current evidence is unavailable, return a typed workflow error rather than inventing approval. The host owns security revocation and permission changes; Hive checks the current supplied workflow delegation status, not global host permission state. Historical approval evidence remains distinct from current delegation; an inactive restored copy does not reactivate delegation.

Same-UID process isolation and independent human identity verification are not Hive acceptance claims. Protect Hive-owned local data with ordinary OS access controls, safe paths and authenticated local DB access where applicable; these are storage safeguards, not an agent security system. Test the deterministic collaboration contract with synthetic evidence, and verify host integration separately without claiming to enforce or replace provider security policy.

Recommended workflow classes: read/inspect within explicit scope; ordinary planning and Issue/Artifact edits, claim/note/submit by the referenced execution-scoped holder with applicable workflow evidence, and explicit user-selected Queen conversation import/export; separate explicit reviewed decisions for Bot registration/retirement, Directive activation, acceptance (distinct reviewer reference, not executor self-accept), uncertain claim recovery, scope expansion and migration/restore promotion (curated Bot memory mutations are proposed deferred beyond MVP). External collaboration representation is **Queen-only**: only Queen may perform authorized external writes on the human's behalf, guided by natural-language policies through existing Directives (no new policy DSL or approval engine), recording meaningful external activity and result references in existing Hive records without a mandatory audit-log subsystem. External write authority must not be delegated to Overlord or Drone; Overlord and Drone have authorized external reads only and prepare proposed external changes, reports, and drafts inside Hive for Queen review. Authorized local work (code edits, tests, local commits) is distinct from external publication. Separate policy from technical enforcement: natural-language policy is not a security boundary; where supported, use host/tool/account permissions, credential separation, and isolation to enforce read-only external access for Overlord and Drone, and document which restrictions are host-enforced versus procedural before dogfooding. Never claim enforcement without evidence or give workers unrestricted external write credentials assuming prompts will prevent misuse. No automatic role or approval creation. Missing stop evidence or required review evidence blocks that transition; Hive does not authenticate the reviewer or observe host execution directly.

Resolver default: no model calls. Resolve explicit target then validated local binding/default; hook invocation requires explicit or prebound target and cannot fall back. Resolve issue owner Area and verify selected Project membership; no guessing among memberships or auto-inheriting memory. Use committed DB snapshot, asset Git tree and installed policy version with fixed observed_at for validity checks. Required inline blocks are role/Soul as applicable, applicable valid approved directives, selected Issue body/acceptance/claim status and latest relevant handoff for resume. Explicitly requested reference/artifact bodies are required for that request; deny unauthorized selection or return CONTEXT_LIMIT rather than silently omit. Then optional authorized relation summaries, in stable category/scope order with updated_at descending and UUID tie-break where relevant (curated Bot memory blocks are proposed deferred beyond MVP; Queen conversation bodies are excluded from `context resolve` by default). Report each omission and continuation; do not load bodies from other scopes or arbitrary paths. No automatic semantic conflict resolution. A context result is data, not authority or proof of host injection. Required blocks take precedence even if optional entries cannot all fit.

Initial limits: 32 KiB default/64 KiB maximum inline UTF-8 body budget; 25 default/100 maximum list page; independently cap serialized context JSON at 512 KiB and typed request at 256 KiB. These are conservative test defaults, not token guarantees; measure and adjust before release. If required bytes exceed either cap, return a typed error with safe bounded references. Repeated equivalent reads against the same snapshot, scope, authority and observed_at have identical content and ordering; do not promise identical timestamps across calls. A changed or invalid applicable workflow scope/evidence invalidates continuation even if DB commit is unchanged; bind cursor to evidence revision or fingerprint and actor reference as well as DB snapshot/query.

#### 2. Transaction and runtime

Retain Rust and local Dolt SQL Server. First prove Linux/local filesystem and pinned Dolt release in synthetic CI, then qualify other platforms independently. One active authority per workspace, verified canonical root and workspace identity, process-held OS lock for all participating Hive writes. No remote lock, independent writable clones, implicit server start or automatic remote sync. Use main only for operational mutations. Lock acquisition is bounded; on contention return LOCK_BUSY, never steal. Start/stop/backup/restore are explicit. Private socket if supported, otherwise authenticated loopback. No credential in argv/logs; no automatic fallback to another endpoint. Exact version/socket/privilege and locking behavior are empirical gates, not guessed capabilities.

Under the exclusive lock: verify active workspace/root and storage authority, normalize request and fingerprint, look up request ID in confirmed history. A matching confirmed receipt returns its original result subject to current workflow scope for inspection, without reapplying mutations or rechecking the stale original expected revisions; a different fingerprint conflicts. Reconcile any pending-request marker before replay or new writes, including when the caller's request ID differs. For a marker with no confirmed receipt, first verify that the earlier server-side transaction has ended or cannot publish. A released process lock, closed client connection and unchanged visible HEAD do not establish that condition. Use positive server-session or verified server-stop evidence and query committed history from a fresh connection. Then require a clean authoritative state at the recorded base or other positive rollback evidence. A pending server transaction or inconclusive observation keeps the marker and blocks unrelated writes. Receipt lookup errors never become NOT_FOUND. For a new request, validate applicable current workflow evidence, expected revisions, graph and claim invariants. Before attempting commit, atomically persist and durably sync a local pending-request marker with the workspace, request ID, base commit, fingerprint and the bounded server/connection identity needed to verify termination. Exclude the payload and credentials. Apply typed changes and receipt in one SQL transaction, confirm the matching durable Dolt version commit, then clear the marker durably and release. Use dolt_transaction_commit=1 only if the spike proves the exact behavior; force commit disabled. On ambiguous outcome, keep the pending marker and recovery-required state that blocks unrelated new writes; reconnect/read retained authoritative history, locate the unique receipt-introducing commit, verify fingerprint/actor and outcome. If the process dies before marker removal, the next writer reconciles it under the same lock. No marker is the source of success; the confirmed receipt and version commit are. If absence is conclusively proven with clean authority, same logical request may retry; otherwise stop. A replay cannot grant a current claim. Prefer one atomic SQL-to-version commit; if not proven, do not adopt that implementation until a tested pending-publication protocol is reviewed. No automatic repair, history rewrite, conflict merge or claim expiry.

Revisions are opaque per aggregate. On an edit increment each existing versioned row whose own fields or directly incident relations change (both endpoints of joins, old/new parents for move, owning Issue for Claim/notes, and owning Bot for memory changes if enabled); require the expected revisions for these rows, not for every transitive descendant. Revalidate all graph/ancestry/readiness invariants under lock, and snapshot-bind derived reads. Store bounded canonical result IDs/revisions and original base commit, actor, authorization reference and validated workflow evidence snapshot in receipt row; SHA-256 fingerprint covers normalized typed operation, resolved workspace/actor/targets, revisions and body bytes (no secrets or raw request in receipt). Exclude the approval/authorization locator itself from the payload fingerprint so a reviewed decision can bind to it without circular hashing; bind and record the actual authorization reference separately. A changed fingerprint with same ID conflicts. Confirmed commit is derived from verified history, never written into its own commit. Keep receipts/history; no automatic cleanup or force rewrite.

#### 3. CLI, Skill and hooks

Use explicit hive --contract 2 and --json (one response envelope on stdout; diagnostics redacted on stderr). Standardize UUIDs for IDs, Issue #number scoped to workspace, common --workspace/--area/--project/--actor options, repeatable --if-match ID=REV, --request-id UUID, --authorization REF or --evidence-file PATH for workflow evidence on mutations (one source), and --file or --stdin body input. The init/start/stop/backup/restore operations act on local runtime or filesystem state and use explicit targets and lifecycle safeguards, not DB mutation receipts or Issue revision flags; promotion remains separate. Conversation import creates a file under the same workspace lock as backup. It uses filesystem verification and atomic publication, with no Dolt mutation receipt or Issue revision flag. Backup and restore apply the conversation selection defined in the [backup and restore contract](#installation-lifecycle-and-recovery). A reviewed command may accept --approval as the specialized authorization reference, never a different permission mechanism. No silent v1 fallback or automatic scope selection. Curated memory CLI commands and typed memory plans are proposed deferred beyond MVP. List/search/show and inspect stay read-only. Mutation receipt and error categories above remain shared. Specific syntax is an initial implementation contract, subject to compatibility tests.

The first writer accepts `issue note ISSUE --kind progress --area AREA --claim CLAIM --actor REF --if-match ISSUE=REV --request-id UUID --file PATH --evidence-file PATH` with an explicit `--workspace`, `--workspace-id`, `--database db` and `--port`. Use exact Issue, Area and Claim UUIDv7s and a UTF-8 body of up to 256 KiB. The Issue must be in progress and its active Claim must match both the Claim ID and actor. The write transaction checks that the owning Area and all its ancestors exist, form an acyclic chain and are active. A replay requires current evidence for the same request and scope and returns the historical result even after the original revision, Claim or Area archival state changes. A deleted receipt in retained history still reserves its request ID.

The decision file is a JSON object with `decision` set to `allow` and an `evidence` object. The evidence carries `version: 1`, `operation: "issue.note"`, `workspace_id`, `request_id`, `fingerprint`, `actor_ref`, `area_id`, `issue_id`, `expected_issue_revision`, `claim_id`, `authorization_ref`, `evidence_id`, `revision`, `source_ref`, `issuer_ref`, `valid_from`, `expires_at` and `withdrawn: false`. The optional `bot_id` is null in this slice. Supply RFC 3339 timestamps that make the decision currently valid. Use nonsecret workflow references for the actual operator decision.

Compute the v1 fingerprint as lowercase SHA-256 of the compact UTF-8 JSON array `[1,"issue.note",workspace_id,area_id,issue_id,actor_ref,claim_id,expected_issue_revision,"progress",body_sha256]`. Compute `body_sha256` as lowercase SHA-256 of the exact file bytes, including whitespace and line endings. Recovery through this writer requires the same verified launch, positive evidence that the prior SQL session ended, and a fresh clean committed snapshot. Use [workspace recover](dolt-workspace-contract.md#workspace-start-stop-and-recovery) after a verified stop. Uncertain termination keeps the marker in place.

The Issue create writer accepts `issue create --area AREA --type TYPE --title TITLE [--file PATH] --actor REF --request-id UUID --evidence-file PATH` with the same explicit workspace and runtime target. It creates one Issue in backlog under the exact active Area and requires active ancestry. It accepts `epic`, `feature`, `task` and `bug`. The title must be nonblank, contain no control characters and fit 255 characters. An explicit file supplies up to 256 KiB of exact UTF-8 body bytes. Omitting the file stores a null body. The guarded transaction advances the exact `issue_number` counter and inserts the Issue and receipt. A missing, zero, stale or exhausted counter blocks the write. Numbers remain reserved in retained Issue history after deletion. The writer refuses allocation if Dolt reports incomplete Issue history, including at a table schema boundary.

For Issue create, use the same decision envelope and common evidence fields with `operation` set to `issue.create`. The exact Area binds the pre-create scope. Omit `issue_id`, `claim_id` and `expected_issue_revision`. Compute the fingerprint as lowercase SHA-256 of the compact UTF-8 JSON array `[1,"issue.create",workspace_id,area_id,actor_ref,type,title,body_sha256]`. Use JSON null for an omitted file and the lowercase SHA-256 of the exact bytes for an explicit file, including an empty file. The receipt result contains `version`, `area_id`, `issue_id`, `number` and `issue_revision`. Replay requires current matching evidence and the Issue's current ownership by the selected Area. It returns the original confirmed result.

Issue create uses a version 2 pending marker with `kind` set to `issue.create` and the newly allocated UUID in `issue_id`. Its other fields and receipt digest follow the version 1 note marker format. The Issue writers can reconcile recognized markers on the same verified launch when it has the grants required by the pending operation. The writer reconciles pending intent before checking grants for a new write. A running launch without the `issues` INSERT grant requires explicit stop and start with the updated binary before creating an Issue. Pending requests require `workspace recover` with the verified stop proof before the workspace can start.

The Linux Issue update writer accepts `issue update ISSUE --area AREA --actor REF --if-match ISSUE=REV --request-id UUID --evidence-file PATH` with the same explicit workspace and runtime target. Select at least one of `--title`, `--file`, `--acceptance-file`, `--priority 0..3`, `--hold REASON` or `--clear-hold`. The Issue and Area selections are exact UUIDv7s. A title follows the create rules. File bytes are UTF-8 and are stored verbatim, including an explicitly empty Issue body. An acceptance file and a hold reason must be nonblank, up to 65,535 bytes each. Hold reasons exclude control characters. The total edit text is bounded at 256 KiB. An omitted field keeps its current value. Hold set and clear are mutually exclusive, and a clear stores SQL NULL.

New edits require active Area ancestry, current ownership and the exact Issue revision. The resulting acceptance criteria must be nonblank for a todo Issue. Title, body, acceptance and hold changes require backlog or todo. A priority-only change is permitted in other lifecycle states because it affects ordering only. Review decisions must still bind the latest Issue revision. The transaction rejects a no-op and a mismatched lifecycle and Claim state. It updates the selected Issue's ordinary fields, revision and timestamp and inserts one receipt. Lifecycle, ownership, Claims and relations remain intact.

Use the request-bound decision envelope with `operation: "issue.update"`, the exact `issue_id` and `expected_issue_revision`. Omit `claim_id`. The optional `bot_id` is null in this slice. The lowercase SHA-256 fingerprint covers compact UTF-8 JSON `[1,"issue.update",workspace_id,area_id,issue_id,actor_ref,expected_issue_revision,[title,body_sha256,acceptance_sha256,priority,hold_edit]]`. Omitted fields are JSON null. The body and acceptance digests cover exact file bytes. For the hold edit, use `[hold_reason_sha256]` for set and `[null]` for clear.

The stored version 1 receipt result contains `area_id`, `issue_id`, `issue_revision` and `fields`, the requested field names in fingerprint order. Confirmation, replay and scoped `operation show` verify the original one-Issue edit and one-receipt introduction against its base commit. They return the Area and Issue IDs and the resulting revision. Replay requires current matching evidence and ownership, and returns the original result after later revisions.

Issue update reuses the version 2 pending marker with `kind: "issue.update"` and the exact edited Issue ID. It uses the existing Issue UPDATE and receipt INSERT grants. After verified stop, `workspace recover` validates the marker with the shared parser and uses the same historical effect verifier as the running writer. A clean store at the recorded base with complete receipt history and no matching receipt supports a rolled-back result.

Before a new Issue write or same-launch reconciliation, Hive verifies the applicable writer table grants. When an older owned launch lacks those grants, use explicit `workspace stop` followed by `workspace start` with the updated Hive binary. If a pending marker exists, verified stop preserves it and workspace start requires reviewed recovery first.

The Linux dependency writer accepts `issue add-dependency ISSUE PREREQUISITE` and `issue remove-dependency ISSUE PREREQUISITE`. Both Issue IDs and both Area IDs are exact UUIDv7s. Supply both scopes for same-Area edits too. Both endpoint revisions advance in the same commit as the one edge change and receipt.

Use the decision envelope with `operation` set to `issue.add-dependency` or `issue.remove-dependency`. The version-1 evidence object has `workspace_id`, `request_id`, `fingerprint`, `actor_ref`, `authorization_ref`, and two grants named `issue` and `prerequisite`. Each grant has `decision: "allow"`, an `endpoint` object with `area_id`, `issue_id` and `expected_issue_revision`, and its own `evidence_id`, `revision`, `source_ref`, `issuer_ref`, `valid_from`, `expires_at` and `withdrawn: false`. The fingerprint is the lowercase SHA-256 of compact UTF-8 JSON `[1,operation,workspace_id,actor_ref,[area_id,issue_id,expected_issue_revision],[prerequisite_area_id,prerequisite_id,expected_prerequisite_revision]]`.

The graph guard checks current ownership, active ancestry, Issue and Claim state, and the bounded stored graph under the workspace lock. For an Issue in progress, in review or done, an added prerequisite must already be accepted as done. A removal preserves all remaining obligations and requires a valid graph at the base. Existing completion states must remain valid. Duplicate additions, missing removals and cycles in either obligation graph fail without a write. The receipt result contains both Issue and Area IDs and both resulting revisions. Replay supplies fresh decisions for both current scopes and returns the original result. Confirmation and recovery verify the exact edge, both endpoint revisions and the decision against the recorded base and introducing commit.

The Linux Artifact writer accepts `artifact create --kind KIND --title TITLE --file PATH --actor REF --request-id UUID --evidence-file PATH` with explicit `--workspace`, `--workspace-id`, `--database db`, and `--port`. Use JSON null for both fields for standalone creation. The optional `bot_id` is null in this slice. Hook adapter is optional: hive --contract 2 --json hook dispatch --stdin accepts a versioned allowlisted JSON object with event, workspace/actor binding, optional Bot/role/Area/Project/Issue IDs, invocation_id and typed preflight/result reference as applicable.
