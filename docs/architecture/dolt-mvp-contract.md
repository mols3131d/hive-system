# Proposed MVP Design Baseline

Status: recommended decisions for review under [#22](https://github.com/mols3131d/hive-system/issues/22). Read with the [redesign](dolt-redesign.md) and [schema](dolt-schema.md). These are proposed replacements, not active workspace policy. User direction establishes Dolt, generic Area/Sub-area, purpose-based Projects, Bot as an inherently Manager identity, role-free slug-based Soul paths, file-based SOUL.md, Dolt-owned curated Memory and the logical latest/core/reference namespace and delegated autonomous Memory curation, with mechanical operations designed for optional lifecycle hooks and security enforcement owned by the provider/harness; other decisions below need review and technical evidence.

## Domain and identity

One authoritative local database per workspace. Area is an untyped recursive scope with a stable UUIDv7 (application-generated, CHAR(36), normalized lowercase). Sub-area is an Area with a parent. Require one owning Area per Issue; an explicitly selected general Area is allowed, never an implicit fallback. Enforce sibling slug uniqueness including roots and prohibit cycles. Moving an Area preserves all IDs. Archive an Area only with no active claims in its subtree; archived ancestry excludes execution and new work until explicitly restored. No automatic archival of children or related Projects.

Project is an independent purpose-based collection of Issues. Membership is optional and many-to-many across Areas. Removing a membership or completing a Project never closes an Issue. Explicitly completing a Project is a planning decision, not acceptance of all members. MVP has no custom project fields, milestones, iterations or project-specific execution status.

Use UUIDv7 primary keys and an immutable workspace-wide issue number for human references (#42). Allocate under the authoritative write lock using a counter row in the same transaction; no MAX+1, reuse or offline allocation on replicas. Import preserves a qualified legacy ID mapping, not necessarily legacy numbers. On restore prohibit concurrent old authority before writes. Area slugs and Bot slugs are locators, not identity. Priority 0–3 (0 highest), NULL unspecified, ordering by priority then creation then ID/number; no priority grants authority. Labels are workspace-wide, normalized and unique. Epic is a grouping Issue, not an executable claim target. Feature, Task and Bug may execute. Parent hierarchy and prerequisite DAG are independent; cross-Area references are allowed with explicit authority. Related/discovered-from links may be deferred; do not misrepresent either as a dependency.

## Work lifecycle and accountability

| Command / transition | Invariant |
| --- | --- |
| create -> backlog | Capture goal; no Claim |
| select backlog -> todo | Verified scope, actionable acceptance criteria, authority; epic may be selected for planning |
| claim todo -> in-progress | Non-epic, ready, fresh expected revision, no active claim; allocate unique claim and holder |
| release/recover in-progress -> todo | Exact claim and verified execution stop; recovery requires authorization |
| submit in-progress -> review | Verified execution stop; evidence and result recorded, remove claim atomically |
| request-changes review -> todo | Record reviewer feedback; new claim required |
| accept review -> done | Authorized acceptance, recorded outcome, required children resolved; no claim |
| submit-epic todo -> review | Explicit proposal after required children resolved; no execution claim |
| cancel nonterminal -> cancelled | Explicit authority and outcome; current claim must first be safely reconciled or released in same guarded change |
| reopen done/cancelled -> todo | Explicit reason/authority; reset closure fields; reconcile downstream and parent outcomes |

Only in-progress may have an active execution Claim; it must have exactly one. Holder is an opaque authorized execution reference, not necessarily a persistent Bot. Planned assignment and reviewer assignment are not exclusive claims; defer a separate assignee field. Claim is not runtime control, credential, or execution permission. No lease, heartbeat, automatic expiry or reassignment in MVP. Stop uncertainty blocks release/recovery/acceptance rather than granting ownership. Epic acceptance requires all children terminal; cancelled children require explicit documented acceptance of the changed scope. The same child-resolution check applies to any parent with children; parentage does not itself create prerequisite edges. Validate a combined completion-obligation graph (Issue -> prerequisites and parent -> children), rejecting cycles even when the individual graphs are acyclic. This check prevents completion deadlocks and does not make parentage a prerequisite or alter ready filtering. Only accepted done satisfies dependencies. Reopen, dependency/parent edits and other changes that invalidate accepted work, current review submissions or running work require explicit reconciliation; reject otherwise. A new unmet prerequisite or changed acceptance criteria cannot silently invalidate a running or review Issue. An accepted parent cannot acquire an unresolved child or retain an invalidated child outcome without explicit reconciliation. No implicit cascade or reopening. Keep progress, evidence, handoff and review notes as intentional typed Issue updates, not logs. Every successful lifecycle transition also appends a system-generated typed transition update in the same transaction, including exact Claim ID/holder and stop/result/review evidence refs where applicable. Acceptance/request-changes must bind the current submission transition and expected Issue revision, and compare the reviewer reference against the submitter and recorded execution holder even after the Claim row is removed. These checks concern workflow references, not authenticated human identity. Generic issue note cannot create or alter transition records.

Ready = todo + executable type + no hold + no current Claim + accepted prerequisites + no archived Area ancestry. Blocked = executable todo not ready, with reason codes; epics are planning-only. Do not store ready/blocked status. Readiness does not grant permission. Claim re-evaluates the predicate in the write transaction.

## Canonical ownership and files

| Data | Canonical owner |
| --- | --- |
| Structured collaboration records, Issue body and updates | Dolt |
| Directive and textual Artifact Markdown body | Dolt |
| Bot registry and Area/resource relations | Dolt |
| Bot Soul (`SOUL.md`) | Native Git tracked Markdown file |
| Bot latest and durable (core/reference) curated memory | Dolt (`bot_memories`); logical `memories/LATEST.md`, `memories/core/`, `memories/references/`; no canonical memory files |
| Large/binary external assets | Existing authorized owner; Resource reference with optional immutable revision/digest |
| Machine config, resource path bindings, local credentials | XDG local environment; never shared |

MVP does not require a managed binary blob store. Reference externally owned files without copying; optional immutable managed blob storage and its recovery protocol are later features. For text artifacts, store Markdown once in Dolt, export on request as a noncanonical copy. Artifact has optional explicit Area, Project, Issue and Resource joins, can be standalone, and does not inherit issue status. Context lookup never treats a matching join as permission to disclose a multi-scope body: default summaries use only directly selected scope/Issue links and explicit workflow scope, without expanding unrelated links. A full body requires explicit selection and coverage of its linked scopes, or an explicit exact-record workflow disclosure declaration; standalone artifacts require explicit selection. Unselected or out-of-scope relation details are not returned. Apply the same rule to cross-Area prerequisite, parent and Resource references; return only permitted metadata or an opaque blocker, not unrelated body text. Preserve existing artifact retention default (three months from applicable substantive event) and work record minimum retention (seven days after relevant event), with retention exceptions, open references and claims protected. No automated deletion or history erasure. Explicit durable archive or verified transfer to canonical owner is a separate decision.

Directive has exactly one scope: workspace, Area or Project. Area descendant applicability is an explicit flag, default false. A project directive applies only when that project is explicitly selected and, if an Issue is selected, the Issue is its member; membership alone is not applicability. An explicitly selected Project-only context may include its directives without sweeping member Issues or their Areas. Workspace/Area ancestry, selected Project, and current Issue are query dimensions, not trust or authority grants. Check source, issuer, validity interval and approval provenance. Conflicting applicable directions stop the affected action for resolution; specificity is not an automatic permission override.

Bot is a registered persistent Manager agent by definition. Registration stores DB metadata without a role column or selector; the sole required Bot content asset is `assets/bots/<slug>/SOUL.md`. Coordinator and Executor are task-scoped responsibilities, not independently registered Bots, and have no independent Soul or Memory. A Bot may coordinate or execute work directly without changing its Manager identity. Role policy remains system-owned. SOUL body contains only identity/purpose/persona for injection; strip management frontmatter from runtime payload. Latest and durable (core/reference) memory are curated Dolt records; recall uses explicit Bot and exact Area scope, no automatic parent/descendant sweep. Logical memory paths are not required files in the asset tree. Do not load README/AGENTS as Bot runtime context; verify host auto-discovery behavior or refuse that activation path. Registry validation checks safe relative paths, expected files and no symlink escape. Registration: prepare and validate asset files and Git commit first, then record registry; failure leaves unregistered files not loadable as a Bot. File edits remain reviewable and independent; capture exact file revision for context. No atomic SQL+Git claim. No secret, raw conversation or personal data capture.

## Local runtime and authority

Recommended Rust CLI + local Dolt SQL Server (MySQL protocol) first. Preserve reusable CLI/config/JSON code. Go embedded is a fallback only if measured setup, latency or reliability warrants a rewrite; CLI subprocess access is a bootstrap/diagnostic candidate, not the normal per-query data path. Pin Dolt and Rust dependency versions after a synthetic spike; verify supported versions at doctor/start. One local server per authorized workspace, explicit start/stop; no auto-install, background scheduler, service registration, external bind or remote exposure. Prefer a private Unix socket and restrictive permissions where supported; otherwise authenticated loopback with unique endpoint. Disable or secure default root access, use limited writer/read-only credentials, redact diagnostics. No credential in Git, DB records, command argv or logs. No Hive HTTP daemon required.

Use an OS-held exclusive advisory lock per canonical workspace for all Hive mutations, maintenance, backup/restore and sync; process death releases it. Local filesystem only, no independent clone or multi-host writers. Use a stable workspace-ID-keyed lock and active-root registration in the single configured local Hive state directory; verify canonical root and DB identity against that registration. A restored copy at another root stays inactive; never create a second active lock just by changing its path. Different state-directory configurations or machines cannot guarantee mutual exclusion; independent writable copies are unsupported. No deleting lock files or stealing based on age. All participating writers must use the lock; direct Dolt administrative writes are explicit offline maintenance with full validation, not normal operation. Raw DB access is not a security boundary against the same OS user. Use read-only access for UI and analysis; do not expose arbitrary mutation SQL. If lock tests or process ownership fail, refuse writes; prefer a verified single writer rather than assuming Dolt merge semantics provide serializable graph invariants. The previous mutation_guard token remains an alternative experimental conflict check, not an MVP dependency.

With lock held, verify storage authority and request identity, resolve existing receipts before checking expected revisions for new mutations, and require a clean/compatible branch main. For a new request, persist a bounded local pending-request marker before attempting commit; begin one SQL transaction, revalidate affected state, apply all changes, store an operation receipt, commit, verify the committed result, then clear the marker before success. Prototype session dolt_transaction_commit=1 with explicit transactions, force-commit disabled; test actual durability/rollback and version commit behavior. Record request ID, operation kind, request fingerprint (no raw confidential payload), result IDs and new revision in the same transaction. On ambiguous result, reconcile by request ID at the authoritative version; same request + fingerprint returns prior result, different fingerprint conflicts. Do not blindly retry or assign execution until verified. Version commit hash is discovered after commit, not written into that same commit. Hold lock through confirmation. If SQL and version commits separate in the tested release, define recoverable pending-publication state before adopting; block subsequent mutations until reconciled. No global ownership from independent replicas.

## XDG and configuration

User configuration: XDG_CONFIG_HOME/hive/config.yml (default ~/.config/hive/config.yml). Workspace data: XDG_DATA_HOME/hive/userdata/ (default ~/.local/share/hive/userdata/), with db/ (Dolt), assets/ (Native Git Bot files), and a nonsecret workspace descriptor with stable workspace ID and schema compatibility. State: XDG_STATE_HOME/hive/ (default ~/.local/state/hive/) for lock, migration/recovery state and redacted diagnostics; socket under valid private XDG_RUNTIME_DIR when available. Never track Dolt internal files in ordinary Git. No secret or host-specific mapping in shared files. Absolute XDG paths only; fallback per specification; explicit invalid selection is an error. Resolve explicit CLI workspace/Area/Project > explicitly configured applicable local binding > user default > validated XDG candidate. A Resource may map to several Areas; return candidates, never silently choose. Project bindings become Area/resource bindings with optional explicit Project; non-Git resources work without Git root. No automatic writes to external projects.

## CLI and API

Commands proposed for MVP; preserve JSON v1 semantics only where compatible, introduce explicit new API/schema version for breaking changes. No silent task-to-issue reinterpretation. Human and machine outputs from shared domain operations.

| Domain | MVP operations |
| --- | --- |
| workspace | init (explicit empty target), status, start, stop, doctor |
| area | create, list, tree, show, move, archive, restore |
| project | create, list, show, add-issue, remove-issue, complete, archive |
| issue | create, list, show, select, ready, blocked, claim, release, recover, submit, request-changes, accept, cancel, reopen, note |
| issue relation | set-parent, add-dependency, remove-dependency, label, unlabel |
| resource | register, list, show, link-area, link-issue |
| directive / artifact | create, list, show, update with revision, link or supersede as applicable |
| bot / memory | list, show, context; authorized reviewed or delegated Dolt memory mutations and explicit Soul file editing; no automatic learning |
| context | bounded resolved issue/area/project context and provenance; no mutation |
| validate | full domain diagnostics |
| backup / restore | explicit consistent snapshot; restore only to separate empty target |

Query through bounded typed filters, sort, pagination and named views. Arbitrary SQL CLI and custom view language deferred; optional read-only SQL client only after permissions and procedure restrictions tested. Global flags: --workspace, --area, --project, --json; issue ID or #number (shell quote if needed). List return observed revision and pagination; context returns selected source refs and excludes unrelated records. Mutations take expected revision where editing existing Issue/record, request ID, explicit target and actor/holder evidence. Stable errors: unresolved_scope, ambiguous_scope, schema_incompatible, invalid_transition, blocked, claim_conflict, stale_revision, authority_unverified, lock_busy, commit_uncertain, constraint_violation. No invented success.

## Backup, sync and migration

Local-first; no remote required or per-change push. MVP consistent backup: quiesce writers and asset edits, verify clean committed DB and asset Git revisions, export to isolated destination with a manifest containing workspace ID, schema version, Dolt commit, asset Git commit and digest of snapshot files; omit credentials and host paths. Validate restore on a fresh target before promoting, verify graph/claims/memory records and Soul files and prohibit overlapping execution authority. Ordinary Git remote is a candidate for Dolt remote; do not conflate Git refs with database refs. Optional remote backup only after synthetic restore and privacy checks. Paired DB/file remote publishing is not atomic; combined remote sync/pull/merge deferred until manifest publication and partial failure recovery are proven. No automatic conflict merge, force push, or independent offline claim coordination.

Migration: inventory legacy files read-only, stop/handoff affected agents, preserve exact old Git ref and policy pin. Produce explicit mapping old scopes -> Areas, Project collections and Issues; preserve references and historical revision evidence. Backlog -> backlog, active todo/in-progress/review/done -> corresponding state, archived -> terminal, but active/uncertain claims require reconciliation; do not fabricate acceptance, silently downgrade or transfer a claim. Preserve legacy date uncertainty; quarantine invalid records rather than inventing values. Map reserved general/userdata scopes explicitly, never infer from repository name. Import directives, text artifacts and bot metadata into Dolt; import verified curated legacy file memory into bot_memories with explicit scope and provenance, keep Soul in the asset tree, and never treat navigation-only files as facts. Preserve uncertain observation dates as unknown. Old memory files remain legacy sources until cutover; no dual canonical originals. Use a new DB/asset tree, dry run on a copy, compare counts, hashes, semantic relationships, missing references, retention and context boundaries; produce import report and legacy ID map. Stop old authority before cutover, obtain approval, update policy and config atomically at the authority-selection boundary. Keep source snapshot read-only for rollback; once new writes occur, rollback requires reconciliation, not silent switch.

## Acceptance and explicit deferrals

Test DDL, unique IDs/numbers/root slugs, FK and graph constraints, all lifecycle transitions, claim races, lock crash/recovery, commit ambiguity/retry, forbidden mutations, backup/restore, safe paths and host context exclusion on synthetic fixtures. Compare Rust SQL connectivity and operational cost before selecting production dependencies. No live data migration, production schema activation, automatic server launch or remote push implied. Later: multi-host authority, background leases/scheduling, generalized SQL query UI, binary store, custom Project fields, broader persistent Bot roles. Canonical legacy policies continue until reviewed replacement.

## Detailed MVP review contracts

The following are proposals for review, not adopted policy or implementation evidence. They refine the preceding baseline with the selected Soul-file/Memory-Dolt storage boundary. Preserve the accepted identity/context boundary in #20 and the XDG direction in #18. Numeric limits, command syntax and candidate schema below are review defaults.

### Bot and curated memory

Keep system-owned Role policy, user-owned Soul, curated memory, work records and harness-owned sessions distinct. A Bot is a persistent Manager agent by definition, with no configurable identity role. Coordinator and Executor are task-scoped responsibilities, not registered identities. A Manager may coordinate and execute directly; delegation depth is optional. Execution responsibility neither changes Bot identity nor grants permission. A runtime session reference is optional, opaque and descriptive; it is neither an authenticated actor nor a Claim. No session table, transcript capture, runtime registry or native memory synchronization.

The selected layout is `assets/bots/<slug>/SOUL.md`, relative to the workspace root (inside the native Git asset tree), with no role directory. Use a workspace-wide unique immutable lowercase kebab-case slug as the human locator and UUID as the relational identity. Never reuse a retired Bot's slug; display name changes do not move the file. Existing paths remain unchanged until explicit migration. System Role policy is versioned with the installed system; Soul contains identity and purpose, not a competing Role policy or authority grant. Any registry identity fields explicitly present in Soul must match; do not require a duplicated role field. Optional README/AGENTS remain management-only. Reject traversal, symlinks/reparse points escaping the asset root, and invalid UTF-8. Never use a Bot asset directory as a host working directory for activation.

Storage decision comparison (Dolt memory selected):

| Criterion | Git Markdown (not selected) | Dolt memory records (selected) |
| --- | --- | --- |
| Canonical body | Scoped files, editable with review | One Markdown body per record, edited through delegated or reviewed domain operation |
| Selection | File manifest and scoped paths | Bot/scope/key index and explicit queries |
| Provenance/revisions | Frontmatter and Git object | Typed metadata and Dolt revision |
| Coordination | Separate Git review and asset snapshot | Common guarded transaction and receipt |
| Restore | DB + Git asset pair | Memory restored with DB; Soul still needs asset pair |

The selected MVP design retains SOUL.md as a file and stores Memory in Dolt. The 24-table DDL remains a candidate pending review and spike. Existing live MEMORY.md files remain unchanged until an approved migration. Preserve #20's semantic distinction: a compact, required latest-memory entrypoint (empty is valid) and optional long-term scoped knowledge. The selected logical namespace is:

```text
memories/
├── LATEST.md
├── core/
└── references/
```

Paths are relative to a Bot's logical namespace. `memories/LATEST.md` is a deterministic Markdown view over curated latest records for the authorized selected scope, empty when none exist; `memories/core/` and `memories/references/` are logical collections of durable records. They are not physical assets, required directories, independently editable originals or an automatic export protocol. Explicit export may render these names outside the canonical asset tree with scope and revision provenance; exports are noncanonical. No implicit write-back. Durable core is default recall and durable reference body is explicit recall. Logical names, category semantics and delegated curation policy are selected; rendering details and initial bounds below are implementation candidates subject to measurement. A single record belongs to exactly one Bot and either global or exact Area scope; Project and Issue are not memory namespaces. Task-specific continuity belongs in Issue handoff/evidence, not memory. Authoritative policy, source facts and reusable procedures remain at their source.

Candidate schema (not active DDL): add one `bot_memories` table with id UUID, bot_id FK, nullable area_id FK, kind latest|durable, recall_tier NULL for latest or core|reference for durable, stable topic_key, title, body, source_ref, author_ref, authorization_mode reviewed|delegated, authorization_ref, optional reviewed_by_ref and reviewed_at (required for reviewed mode, absent for delegated), observed_at (nullable for unknown legacy dates), revision, created_at, updated_at, retired_at and retirement_reason. All three categories may be global or explicitly scoped to one Area. Default recall includes latest and durable core for the selected exact Area plus non-scope-specific global records, within the context budget; durable reference bodies require explicit selection. Never include unrelated Area knowledge. Enforce uniqueness of live (bot_id, scope, topic_key) under the common lock including NULL scope, same key retained on update; no duplicate copy between categories. Classifying latest as durable core or reference, or changing durable recall tier, updates the same record's kind/tier, keeps its UUID and scope, and requires verified delegated authority or explicit review. A new durable record may be created directly when justified. Scope changes and restoration require separate explicit approval and guarded validation. Require nonempty source/evidence and applicable workflow evidence; a reference alone is not a complete workflow decision. Retire rather than purge, exclude retired from recall; history/backups may retain content. No secrets or information requiring guaranteed erasure. An empty memory namespace is normal. Initial migration maps legacy general to global, other scopes to explicit Areas; distinguish navigation-only root MEMORY.md from actual curated learning. Quarantine ambiguous scope, duplicates and conflicting facts rather than manufacturing evidence.

Curate explicitly: the user supervises and grants or revokes authority; the Bot selects reusable verified learning, checks sources and existing keys, and manages its own memory. Coordinator/Executor provide evidence or suggestions, not direct memory mutations. With verified explicit user delegation bound to workspace, Bot, exact scopes, operations and validity, a Bot may create, update, reclassify and retire its own latest/core/reference records without individual user approval. Without a valid grant, require explicit review or return a proposal only. Scope moves/expansion, restore and cross-Bot disclosure require separate explicit authorization; no cross-Bot direct mutation by a Bot. Soul, Role, Directive and permission changes are outside memory. No secrets, personal data, raw conversations or unverified claims. Authorization is checked at mutation time under the authoritative lock; record the actual mode/reference and actor, not invented review evidence. The workflow evidence contract is specified in the execution defaults below. The provider/harness or human operator owns authentication, approval interaction, execution permissions and isolation. Hive verifies workflow evidence consistency and scope, not authenticated identity. Do not enable delegated writes before workflow evidence validation is tested.

Latest is curated recent reusable knowledge, not a transcript or Issue progress store. At explicit learning or curation requests, preserve currently useful recent knowledge, promote repeatedly useful knowledge to durable core, move specialized reusable knowledge to durable reference, consolidate duplicates or retire invalid/obsolete entries. Direct durable creation is permitted. Keep stable IDs on classification changes. Age and usage can inform inspection but are not semantic proof; never auto-promote, merge, retire, expand scope or delete based on them. Reads and session starts do not mutate. No mandatory session-end save, automatic extraction, scheduler or LLM calls in Hive. Optional host lifecycle hooks may invoke read-only inspection and context resolution, or dispatch an already explicitly authorized typed operation through the same guarded CLI; the event alone never authorizes a write.

Mechanical operations: list exact scoped keys and deterministic candidate reports (usage of byte limits, age, same-key conflicts, exact body equality within authorized scope, missing source metadata); distinguish verified source availability from truth and unverifiable external references. Report only; the Bot decides semantic conflicts, usefulness, classification and edits. Candidate inspection is read-only, bounded and does not fetch external resources. Render LATEST.md from global and selected exact Area sections using updated_at descending then UUID ascending, with title/body/source ID and snapshot provenance; no implicit summary or file write. An empty scope is valid.

Initial size contract for testing: latest aggregate 2 KiB and durable core aggregate 4 KiB per Bot and exact scope (including NULL global); each latest/core body at most 1 KiB; each reference body at most 16 KiB. Global plus one Area defaults to at most 12 KiB of memory bodies. Count UTF-8 body bytes, separately track metadata and serialization. Check final aggregate totals under the common lock, reject limit violations without side effects. Permit explicit atomic curation batches of typed edits with expected revisions for all touched records and one request ID/receipt; verify all authorization, scope, live-key uniqueness and size invariants for the final state. A read-only plan/preview is advisory; revalidate against fresh state before apply. No silent truncation, overwrite, eviction or implicit mutation.

File import/export is explicit and exported copies are noncanonical. Existing Git review workflow in #20 remains active until reviewed adoption. Dolt writes require verified authorization, revision and receipt; no bypass. Registration validates Soul only; empty memory is valid. Restore verifies memory ownership, scope, content and provenance with the DB and Soul against the paired Git snapshot. Physical deletion/history erasure is outside normal MVP operations.

### Context resolution

Inputs: explicit workspace, actor/role, optional registered Bot ID, Area ID, optional Project ID, optional Issue ID, explicit memory selection and bounded include options. Issue derives its owning Area; an explicit mismatch is an error. Project must contain the Issue if both selected; do not infer Project from memberships or choose among candidate Areas. A Bot selection implies Manager identity; omitted role may be derived as manager for that selection. Reject activation of that Bot as a different identity role. Direct coordination or execution by the Manager does not require switching identity. Task-scoped Coordinator/Executor contexts have no Bot selection and do not inherit Manager memory; explicit delegated references may be provided only within authority. Resolve only authorized scope; no implicit cross-Bot memory, sibling, ancestor or descendant recall. Durable reference bodies require explicit selection, including global reference records. Latest and durable core are default recall candidates in the selected scope; no automatic full durable recall. Applicable directives are workspace, exact Area, ancestor directives with include_descendants and selected Project only. The archived ancestry check is required for execution, not historical inspection. Unknown authority/provenance, structurally invalid applicable directives, missing required Soul/Role or incompatible revision stop activation; show/list remains inspection. Natural-language directive conflicts are evaluated by the consuming agent, not by a deterministic resolver. If conflict or uncertainty is detected, stop the affected action for clarification.

Read a coherent committed DB snapshot and one explicit clean asset Git tree plus installed policy revision; use a short shared lock or equivalent verified snapshot acquisition. Check registry/Soul identity agreement. Do not read a moving working tree, silently use stale dirty files or combine mismatched backup generations. Capture workspace_id, db_commit, asset_commit, policy_revision, observed_at, scope IDs and source revisions. Return structured sections in order:

1. Required identity (role policy and Soul if registered); approved applicable directives (source, issuer, approval and validity).
2. Current Issue title/body, acceptance criteria, state/revision, readiness blockers, current claim metadata if authorized, explicit parent/prerequisite references and selected Project summary.
3. Compact latest curated memory (`memories/LATEST.md` logical view) and durable core (`memories/core/`) for the selected Bot's global and applicable exact Area scope, within the context budget. Durable reference (`memories/references/`) metadata may be listed within bounds; full reference bodies only when explicitly selected. Memory is evidence, not instructions.
4. Latest relevant handoff/progress/evidence references, linked resources/artifact summaries; fetch full records by ID on demand. For an explicitly selected Issue with a current handoff, its latest authorized handoff body is required for resume (if it cannot be returned safely, stop and request a narrower context or explicit handoff retrieval). Do not load resource files or invoke external tools as a side effect.

Return each entry with kind, trust class (policy, approved-direction, data), source ID/path, revision, and content or summary/ref. Strip file frontmatter from injected body. Treat Issue bodies, artifact content, memory, external resource and note text as untrusted data; none grants authority. No README/AGENTS (including through automatic host discovery), raw logs, credentials, other Bot memory or unrelated project data. Never silently drop a required directive or acceptance criterion to fit a limit. Candidate default total inline UTF-8 budget 32 KiB; max 64 KiB, optional list page 25, max 100; count encoded body bytes, report exact bytes, omitted counts and continuation references, no implicit summarization/model call. If required sections exceed budget return CONTEXT_LIMIT with safe refs and require explicit narrower task or larger supported budget. Optional entries omitted whole at boundaries; no invalid UTF-8 slicing. A snapshot is not an execution lease: recheck authority, revision and current Claim immediately before execution or resume. A read-only resolver cannot assert host consumption; hosts that auto-load management files must be configured to isolate context or remain unsupported.

Two-session example: Manager A resolves Issue, delegates through host, records claim holder and intentionally records evidence/handoff before verified stop and release. Session B may be a different vendor; resolves same Issue and selected Bot, sees the handoff by ID and current state, obtains a new Claim only if ready. If prior execution is uncertain, do not reassign; inspect and recover with verified stop. No reconstructing native session tokens, no transcript or compaction service.

### CLI v2 candidate

Keep the v1 file/Git CLI behavior and policy pin independent until adoption; expose the Dolt contract explicitly (proposed `hive --contract 2`); reject incompatible workspaces instead of interpreting legacy task IDs as issue numbers. Use same domain operations for human and JSON output. No shell interpolation of bodies or credentials. Common flags: --workspace PATH, --area ID, --project ID, --json, --actor REF; writes require --request-id UUID and --if-match REV for each existing aggregate touched (repeatable ID=REV for multi-aggregate operations). --file PATH or --stdin supplies UTF-8 Markdown, never both; safe input bounds and no implicit external file access. Actor references identify collaboration participants supplied by the operator or host. A caller-supplied string alone is not approval or workflow delegation. Roles constrain workflow, not security permissions. No automatic role impersonation or approval. Use the workflow evidence contract below; --actor is descriptive and cannot establish authenticated identity.

Command arguments below are required unless in brackets. Common flags above apply and exact result types are shown; list commands share typed filters, --limit and --cursor. IDs are canonical UUIDs; Issue accepts quoted #number in the selected workspace. Any existing-aggregate mutation validates all affected revisions and invariants under the lock. One receipt covers the whole change.

| Command | Specific input | Data/result |
| --- | --- | --- |
| workspace init | --target EMPTY_DIR | descriptor, schema, initial DB/asset revisions |
| workspace status / doctor | workspace | observed identity, versions, state, diagnostics; no repairs |

### Shared Skill procedure

Use distributable Rulesync source, not generated vendor assets. Skill is instructions for the host, not an executor or approval service. Establish exact workspace/role and applicable user authority; doctor/status then context resolve. Inspect only selected scope; list ready or inspect specific Issue; blocked work remains blocked. Manager plans/delegates, Coordinator coordinates, Executor performs approved task; no automatic runtime invocation assumed. Before execution acquire/verify exact Claim, check fresh authority and required context. Use host-native execution only within authorized scope. Record concise progress, evidence and handoff as Issue notes/artifacts; do not log all conversation. Confirm stop from actual host or authorized external evidence, then release or submit with exact Claim. Reviewer independently accepts or requests changes; no automatic self-accept. Uncertain stop or commit means halt and reconcile; never recover automatically. Resume in another session by fresh resolution and current claim check, not previous conversation. Memory curation is a separate intentional action under verified review or user delegation; use mechanical inspection for candidate detection, then explicit bounded changes. No automatic semantic curation. Skill consumes v2 JSON and handles errors without assuming command success, and must not install/configure hosts or modify external repositories without explicit authorization.

### Optional lifecycle hook boundary

Prefer mechanical and hook-callable operations. Hooks are optional thin invocation paths over the same versioned CLI/domain contract used by Skill and manual clients. Do not require a specific host, add a separate runtime or event store, or install/modify host settings automatically. Vendor event mappings and delivery/injection support must be verified per host; unsupported or absent hooks use the identical manual/Skill path. The hook-ready interface is in MVP design scope; vendor-specific integration packages and mandatory automatic injection are not.

| Logical event candidate | Deterministic operation |
| --- | --- |
| session_start | Resolve explicit workspace/Bot/scope and return bounded context; no implicit initialization |
| session_resume | Refresh context and report current Claim/revision; never reassign |
| before_compaction | Inspect current Issue/Claim/handoff state; no transcript capture or forced save |
| after_compaction | Refresh selected context from canonical records; no native session reconstruction |
| before_action | Validate exact Hive-related action against current authority, Claim if applicable, and revisions |
| after_action | Validate explicitly supplied typed result or inspect state; no raw tool output capture |
| session_end | Inspect memory size/curation candidates and unresolved work; no automatic release, retirement or forced save |

These are conceptual names, not a claim that any host exposes these events. Only use events actually supported by the host. Do not observe or intercept unrelated host activity; host-independent domain guards must always run at the actual mutation boundary, even without a hook. A before_action check is not a lease or permission grant and cannot guarantee that an external action is blocked by the host. A session_end or compaction event is not proof an execution stopped.

Contract candidate: pass only allowlisted explicit workspace/actor/Bot/scope IDs, event kind, optional opaque invocation correlation ID and typed operation references where needed. No prompt, raw transcript, tool output, credentials or arbitrary executable text in the hook payload or diagnostics. Use bounded versioned JSON responses (context, report, or typed error), bounded invocation timeout, explicit status, and no ambient default to a different scope. A hook cannot start a daemon, acquire/release a claim, run an agent, grant approval, or choose semantic memory edits merely because an event fired. To automate application of an already authorized typed change, explicitly dispatch the same mutation API with verified grant, expected revisions and request ID; repeated deliveries reuse the same request ID for the same logical mutation. Do not derive authority from event IDs or caller labels. Missing/stale/revoked authorization rejects writes. Read-only hooks are safe to repeat and have no DB side effects; no new hook event table, persistent event log or retry queue.

If required context or validation is unavailable, report a typed error and stop the affected Hive workflow; no silent fallback to stale context. For advisory inspection, report failure without changing state or blocking unrelated host activity. Respect host timeout and failure semantics; if the host cannot enforce required preconditions, use explicit Skill/CLI checks or do not support that activation path. Never claim successful injection or interception without host evidence. Verify hook and manual parity, repeated/missing/out-of-order events, timeout, scope/authority failure, and non-interference on synthetic inputs before supporting a host mapping. Use the hook dispatch and bounded request defaults below; supported host mappings and timeout behavior require evidence.

### Installation, lifecycle and recovery

Recommended first target: Linux on a local filesystem with verified process-held locks; other Unix platforms including macOS are not claimed supported until equivalent tests pass. Pin tested Dolt release, Rust dependencies and supported platform in release manifest; no version claim before spike. Installation copies verified binary and distributable Skill to explicit user destinations; no auto-start/service/host integration. Doctor checks binary version, XDG absolute paths and owner/mode, supported filesystem/lock, free space, endpoint, schema, matching workspace descriptor/DB identity and clean authority; read-only, never prints credentials. Unsupported platform or path refuses operation rather than falling back silently.

Init only on explicit empty target (no symlink escape), initialize DB main/schema/ledger/counter, Git asset tree and descriptor in isolated staging; verify consistency before publication. Failed init preserves clearly marked partial staging and does not select it. Recommend local restrictive directories/files (0700/0600 where supported). Keep endpoint, PID/process-start identity, runtime nonce, local credentials and recovery markers outside tracked data. Use a private runtime socket if supported by pinned Dolt; else authenticated loopback, no external listener. No ambient root/no-password access; separate constrained reader/writer identities, tested procedure privileges. Resolve the lock by workspace ID within the configured canonical local state directory, verify registered active root plus DB identity, and reject inactive roots. Different state namespaces are not an isolation guarantee. Keep lock file inode stable; never unlink to steal.

Start under lock, verify no competing process/endpoint, launch explicit Dolt process, verify identity/database and connection using bounded timeout before reporting running; failure reports stopped or unknown, not success. Stop under lock only verified owned process; drain Hive writes, request graceful stop, check actual exit; never kill arbitrary PID or clear a claim. PID reuse, stale marker and unexpected external server require inspection and safe refusal. Status distinguishes uninitialized, stopped, running, incompatible, recovery-required, unknown. No automatic repair or restart. Crash releases OS lock; next writer checks the durable pending-request marker, dirty DB working set, unresolved receipts and storage authority before any mutation. A pending marker must be reconciled even when the DB working set is clean. If SQL commit/version commit split, require explicit recovery protocol and block new writes until identified commit or rollback proven; never delete state to resolve ambiguity. Execution may continue outside Hive after DB stop; never infer worker stop from server shutdown.

Backup: take exclusive workspace lock and require quiesced asset editors; require committed DB and clean asset Git tree; refuse pending writes or unknown claims/execution state for promotable backup. Export Dolt-native recoverable snapshot with history and Git asset snapshot with history into new staging destination, not a copy of live database files. Manifest includes format version, workspace ID, schema, Dolt version/commit, asset Git commit, policy revision, relative file paths, SHA-256 digests, creation time, and consistency state; no credentials, local bindings, host paths or logs. Verify actual revisions and digests before final atomic publication within same filesystem; incomplete snapshot never usable as completed backup. Explicit destination only, no network or remote push. A known active claim may be preserved in an inactive forensic snapshot only if explicitly classified non-promotable; never clear it during export.

Restore checks manifest/version, safe relative paths, digest and exact revisions before importing to separate empty target. Use isolated restore staging, validate schema, graph, IDs, receipt history, assets and claims; compare logical row counts and content hashes. Keep workspace identity, regenerate only machine-local bindings/credentials after verification. Restore returns an inactive copy without active workflow delegations, host authorization or credentials; an operator or host must supply current applicable workflow evidence before writes. Explicit authority promotion requires old writers and external executions stopped, review of all claims and separate authorization. Two writable copies with same identity unsupported. No automatic authority switch, overwrite, merge, rollback of live state or deletion of original. Malformed/incomplete snapshot remains isolated, no writes to original. Remote backup/merge remains a synthetic spike and future review item.

### Execution defaults and decision gates

The following implementation defaults are selected as a delegated design recommendation, not an adopted security policy or authorization to write real data. Preserve the current v1 implementation, policy pins, independent branches and live records. No new service, agent runtime, event bus, RBAC subsystem or external project modifications.

#### 1. Context and authorization

Security ownership is outside Hive. The human operator, agent provider, host harness and OS own authentication, permission prompts and enforcement, sandboxing, process isolation and execution controls. Hive is a collaboration and context system, not an IAM system, credential broker, approval UI or security enforcement layer for arbitrary agent actions. It must not install or override host security settings, require a particular provider, or promise that actor references identify an authenticated person. No independent security trust model, actor authentication, mandatory local authority manifest or separate grant registry is required.

Hive retains domain workflow guards: explicit participant references, work ownership, Claim, scoped Bot memory, applicable directives, delegation and review evidence, allowed workflow operations, expected revisions and state transitions. Keep these independent of external security permissions. A host-approved tool call alone does not establish an Issue acceptance, execution stop or Memory scope expansion; a Hive Claim or workflow delegation alone does not authorize external tool actions. Hive validates structural evidence, referential consistency and applicable scope, not the authenticity of the host or user.

For delegated or reviewed operations, accept a versioned, nonsecret workflow evidence object or an explicit reference to such a record supplied by the operator/host. The minimal evidence binds workspace, actor reference, optional Bot, exact Area/Issue scope, operation allowlist, evidence ID/revision, source/issuer reference and applicable validity interval/withdrawal status. Reviewed decisions additionally bind the request ID, canonical payload fingerprint, affected expected revisions, outcome and reviewer reference distinct from the submitting executor where required. Reject missing, malformed, expired, withdrawn, mismatched or unresolved evidence; revalidate supplied/resolved current evidence and expected revisions at the mutation boundary. Do not infer grant scope from Project membership, parent Area, Bot identity or event name. Do not fabricate approval or assert that a matching reference proves authenticated identity. Explicit user/host workflow declarations are inputs, not security credentials. Keep only nonsecret workflow provenance in Hive records/receipts; persist the minimal validated canonical workflow evidence snapshot in the receipt at mutation time, not the raw input. It records what was declared at the time, not a live grant; no tokens, provider credentials or raw approval transcripts. Evidence may be supplied directly as a bounded typed declaration for the current invocation, or resolved from an explicitly selected local canonical collaboration record or operator/host source; no mandatory new registry, service or external fetch. A bare ref or previously saved receipt is insufficient for a new delegated write. For CLI and hook requests use explicit --evidence-file or an allowlisted typed evidence object in the request, mutually exclusive with a resolvable evidence ref. The host supplies current declarations; without an available current source Hive cannot detect revocation elsewhere and must not claim to do so. If current evidence is unavailable, return a typed workflow error rather than inventing approval. The host owns security revocation and permission changes; Hive checks the current supplied workflow delegation status, not global host permission state. Historical approval evidence remains distinct from current delegation; an inactive restored copy does not reactivate delegation.

Same-UID process isolation and independent human identity verification are not Hive acceptance claims. Protect Hive-owned local data with ordinary OS access controls, safe paths and authenticated local DB access where applicable; these are storage safeguards, not an agent security system. Test the deterministic collaboration contract with synthetic evidence, and verify host integration separately without claiming to enforce or replace provider security policy.

Recommended workflow classes: read/inspect within explicit scope; ordinary planning and Issue/Artifact edits, claim/note/submit by the referenced holder with applicable workflow evidence, and self-memory curation within delegated scope; separate explicit reviewed decisions for Bot registration/retirement, Directive activation, acceptance (distinct reviewer reference, not executor self-accept), uncertain claim recovery, scope expansion and migration/restore promotion. Destructive or external action remains subject to operator/host authorization. No automatic role or approval creation. Missing stop evidence or required review evidence blocks that transition; Hive does not authenticate the reviewer or observe host execution directly.

Resolver default: no model calls. Resolve explicit target then validated local binding/default; hook invocation requires explicit or prebound target and cannot fall back. Resolve issue owner Area and verify selected Project membership; no guessing among memberships or auto-inheriting memory. Use committed DB snapshot, asset Git tree and installed policy version with fixed observed_at for validity checks. Required inline blocks are role/Soul as applicable, applicable valid approved directives, selected Issue body/acceptance/claim status and latest relevant handoff for resume. Explicitly requested reference/artifact bodies are required for that request; deny unauthorized selection or return CONTEXT_LIMIT rather than silently omit. Then optional exact-Area latest/core, global latest/core, bounded reference metadata and authorized relation summaries, in stable category/scope order with updated_at descending and UUID tie-break where relevant. Report each omission and continuation; do not load bodies from other scopes or arbitrary paths. No automatic semantic conflict resolution. A context result is data, not authority or proof of host injection. Required blocks take precedence even if default memory cannot all fit.

Initial limits: 32 KiB default/64 KiB maximum inline UTF-8 body budget; 25 default/100 maximum list page; independently cap serialized context JSON at 512 KiB and typed request at 256 KiB. These are conservative test defaults, not token guarantees; measure and adjust before release. If required bytes exceed either cap, return a typed error with safe bounded references. Repeated equivalent reads against the same snapshot, scope, authority and observed_at have identical content and ordering; do not promise identical timestamps across calls. A changed or invalid applicable workflow scope/evidence invalidates continuation even if DB commit is unchanged; bind cursor to evidence revision or fingerprint and actor reference as well as DB snapshot/query.

#### 2. Transaction and runtime

Retain Rust and local Dolt SQL Server. First prove Linux/local filesystem and pinned Dolt release in synthetic CI, then qualify other platforms independently. One active authority per workspace, verified canonical root and workspace identity, process-held OS lock for all participating Hive writes. No remote lock, independent writable clones, implicit server start or automatic remote sync. Use main only for operational mutations. Lock acquisition is bounded; on contention return LOCK_BUSY, never steal. Start/stop/backup/restore are explicit. Private socket if supported, otherwise authenticated loopback. No credential in argv/logs; no automatic fallback to another endpoint. Exact version/socket/privilege and locking behavior are empirical gates, not guessed capabilities.

Under the exclusive lock: verify active workspace/root and storage authority, normalize request and fingerprint, look up request ID in confirmed history. A matching confirmed receipt returns its original result subject to current workflow scope for inspection, without reapplying mutations or rechecking the stale original expected revisions; a different fingerprint conflicts. For a new request, validate applicable current workflow evidence, expected revisions, graph and claim invariants. Before attempting commit, atomically persist and durably sync a local pending-request marker (workspace, request ID, base commit, fingerprint; no payload or credentials). Apply typed changes and receipt in one SQL transaction, confirm the matching durable Dolt version commit, then clear the marker durably and release. Use dolt_transaction_commit=1 only if the spike proves the exact behavior; force commit disabled. On ambiguous outcome, keep the pending marker and recovery-required state that blocks unrelated new writes; reconnect/read retained authoritative history, locate the unique receipt-introducing commit, verify fingerprint/actor and outcome. If the process dies before marker removal, the next writer reconciles it under the same lock. No marker is the source of success; the confirmed receipt and version commit are. If absence is conclusively proven with clean authority, same logical request may retry; otherwise stop. A replay cannot grant a current claim. Prefer one atomic SQL-to-version commit; if not proven, do not adopt that implementation until a tested pending-publication protocol is reviewed. No automatic repair, history rewrite, conflict merge or claim expiry.

Revisions are opaque per aggregate. On an edit increment each existing versioned row whose own fields or directly incident relations change (both endpoints of joins, old/new parents for move, owning Issue for Claim/notes, owning Bot for memory changes); require the expected revisions for these rows, not for every transitive descendant. Revalidate all graph/ancestry/readiness invariants under lock, and snapshot-bind derived reads. Store bounded canonical result IDs/revisions and original base commit, actor, authorization reference and validated workflow evidence snapshot in receipt row; SHA-256 fingerprint covers normalized typed operation, resolved workspace/actor/targets, revisions and body bytes (no secrets or raw request in receipt). Exclude the approval/authorization locator itself from the payload fingerprint so a reviewed decision can bind to it without circular hashing; bind and record the actual authorization reference separately. A changed fingerprint with same ID conflicts. Confirmed commit is derived from verified history, never written into its own commit. Keep receipts/history; no automatic cleanup or force rewrite.

#### 3. CLI, Skill and hooks

Use explicit hive --contract 2 and --json (one response envelope on stdout; diagnostics redacted on stderr). Standardize UUIDs for IDs, Issue #number scoped to workspace, common --workspace/--area/--project/--actor options, repeatable --if-match ID=REV, --request-id UUID, --authorization REF or --evidence-file PATH for workflow evidence on mutations (one source), and --file or --stdin body input. The init/start/stop/backup/restore operations act on local runtime or filesystem state and use explicit targets and lifecycle safeguards, not DB mutation receipts or Issue revision flags; promotion remains separate. A reviewed command may accept --approval as the specialized authorization reference, never a different permission mechanism. No silent v1 fallback or automatic scope selection. Typed memory plans contain schema_version, Bot/scope, operations, expected revisions and request ID; no executable text, use canonical validation under lock. List/search/show and inspect stay read-only. Mutation receipt and error categories above remain shared. Specific syntax is an initial implementation contract, subject to compatibility tests.

Hook adapter is optional: hive --contract 2 --json hook dispatch --stdin accepts a versioned allowlisted JSON object with event, workspace/actor binding, optional Bot/role/Area/Project/Issue IDs, invocation_id and typed preflight/result reference as applicable. Read-only only; no transcript/prompt/tool output, no arbitrary command, no automatic write. A host may invoke an ordinary explicitly authorized mutation separately with stable request ID; same guards. Hook returns the shared response envelope; timeout default 5 seconds, maximum configurable 30 seconds, bounded by host timeout; no implicit retry or side effect. On timeout/unsupported event/invalid scope return a typed failure; required Hive precondition fails closed, advisory inspection may be skipped without modifying state or blocking unrelated activity. Use existing Skill/manual fallback. No host package, event store or runtime dependency. Test hook/manual parity and non-interference; qualify each host mapping individually.

#### 4. Installation, backup and migration

Use explicit verified binary/Skill installation and existing XDG precedence. Init/start/stop/status/doctor as above. No global host config changes, daemon installation or project writes by default. Back up committed Dolt history and clean Soul asset Git revision into a new local destination with manifest/digests; no automatic remote, active host permissions, credentials, or machine bindings included. Restore to a separate inactive target and verify graph, memory, receipts and paired revisions. Keep original authority and claims until verified stopped. Historical workflow evidence snapshots are retained with the DB receipts and transition updates and verified during restore. Legacy or external historical references not captured in the DB may be reconciled by explicit local export of minimum nonsecret provenance; never include active host permissions or profile bindings. If required historical evidence is unavailable, permit structural inspection only; refuse affected activation or authority promotion until reconciled. No delegation is activated by restore. Never copy the live DB directory while running. Migration is a separately reviewed dry-run on disposable authorized copies with qualified ID mapping, explicit scope mapping, no fabricated evidence, count/content/graph checks and rollback plan. Existing work remains v1 until cutover is explicitly authorized. No destructive cleanup, remote publishing or live authority switch based on this draft.

#### 5. Implementation order and acceptance

Implementation order: (1) isolated Dolt spike and pinned release evidence before contract adoption; after review of that evidence and adoption, (2) schema, domain validation and transaction/receipt core; (3) workflow evidence, scoped reads and context; (4) typed mutations, claims, memory and recovery; (5) CLI/Skill/hook and installation/backup/restore; (6) synthetic end-to-end acceptance and migration dry-run. Keep existing v1 compatible and preserve independent work.
